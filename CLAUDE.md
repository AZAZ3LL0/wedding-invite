# CLAUDE.md

Свадебный сайт-приглашение с RSVP и Telegram-ботом. Разработчик один, сессий много. Этот файл держит сессии в одном русле.

## Источник истины

Прочитай `tech.md` в корне репозитория перед любой работой. Он описывает стек, схему БД, контракты очереди и бота, общие типы, список UI-примитивов, дизайн-токены, стратегию тестов и дорожную карту. Подчиняйся ему дословно.

Приоритет при конфликте: `tech.md` → существующий код → эта инструкция → твои предпочтения. Если код противоречит `tech.md`, чини код, а не спецификацию.

## SPEC GAP

Не хватает контракта, типа, поля в схеме, топика очереди или формата роута — **СТОП**. Не выдумывай тип и не пиши код против воображаемого контракта. Выдай блок:

```
SPEC GAP
Что нужно: <поле / тип / топик>
Зачем: <какой сценарий блокирован>
Предлагаемая форма: <точное определение>
Затрагивает: <какие таблицы, слайсы, тесты>
```

Дальше работай на локальной заглушке, помеченной `// SPEC GAP: <короткое описание>`. После моего решения впиши контракт в `tech.md`, добавь строку в changelog, бампни версию ядра, замени заглушку.

Это правило важнее скорости. Разойтись со спецификацией дешевле поймать сейчас, чем через три сессии.

## Эталон

Любая новая фича повторяет раскладку эталонного слайса `routes/(guest)/[code]/rsvp`: домен в `lib/server/<домен>` → `load` и actions в `+page.server.ts` → страница → локальные компоненты рядом. Не изобретай свою структуру, сверься с эталоном.

## Одна задача за раз

Реализуй одну задачу из дорожной карты `tech.md` и остановись. Не разворачивай весь этап и не трогай соседние стадии «заодно». Сфокусированный дифф важнее объёма.

Перед началом задачи назови в двух-трёх строках: что делаешь, какие файлы трогаешь, какие контракты и типы затрагиваешь, какие тесты пишешь. Если план расходится с `tech.md`, скажи об этом до кода.

## Чек-лист перед завершением задачи

Пройди механически, по пунктам:

- [ ] нет выдуманных типов, всё из `tech.md`;
- [ ] использованы примитивы из `lib/ui`, а не самописный UI;
- [ ] `guestId` в action проверен на принадлежность invite из URL — первой строкой;
- [ ] серверные данные не утекли в клиент (`adminComment`, чужие блоки, соседние приглашения);
- [ ] контент чужой аудитории отфильтрован на сервере, не скрыт CSS;
- [ ] для каждого джоба есть тест идемпотентности (два прогона — один эффект);
- [ ] на стыке есть контрактный тест против zod-схемы;
- [ ] тесты выведены из критериев приёмки, а не из реализации;
- [ ] анимации только `transform`/`opacity`, `prefers-reduced-motion` уважается;
- [ ] `pnpm lint`, `pnpm check`, `pnpm test`, `pnpm build` зелёные.

## Что не делать

- Не писать и не править SQL-миграции руками. Схема правится в `lib/server/db/schema.ts`, миграции генерятся `pnpm db:generate`.
- Не добавлять зависимости без явного согласования. Тяжёлые анимационные библиотеки, UI-киты и конструкторы форм запрещены `tech.md`.
- Не вызывать реальный Telegram API в разработке и тестах. Только `FakeTelegramClient`, флаг `USE_FAKE_TELEGRAM`.
- Не хранить данные гостей во внешних сервисах и не подключать аналитику с cookie.
- Не менять `tech.md` мимоходом внутри фичевой задачи. Правка ядра — отдельный шаг с бампом версии.
- Не писать тесты, которые повторяют реализацию и зеленеют всегда.

## Коммиты

Conventional Commits, английский, `type(scope): summary`, императив, до ~50 символов, без точки. `type ∈ feat|fix|test|refactor|chore|docs`.

Коммить сама по ходу работы, маленькими логическими коммитами после каждого осмысленного шага. Не сваливай задачу одним коммитом в конце. Каждый коммит по возможности проходит тайпчек.

Примеры: `feat(rsvp): add companion seat check`, `test(queue): assert reminder handler idempotency`, `fix(telegram): mark chat blocked on 403`.

## Стиль

Код и комментарии — английский, интерфейс сайта — русский. Комментарии объясняют *почему*, не пересказывают код. `any` запрещён. Внешние данные проходят Zod.

Проза (сообщения, документация, тексты интерфейса): активный залог, конкретика, без филлеров, без em-dash, без эмодзи. Кнопка называет действие и сохраняет имя во всём потоке.
